# F405 USB 接收超时现场记录

本版仅增加普通 RAM 诊断，不取消接收、不改写 USB 寄存器、不自动恢复、不改变握手或 SD 文件内容。主板代码未修改。新增注释和本文均为 UTF-8。

## 触发条件

`usb_task.h` 的 `USB_RX_TIMEOUT_MS` 默认 1000 毫秒：应用处于 `APPLICATION_READY`，同一次接收请求的 `usb_rx_pending` 持续置位达到阈值时抓取一次现场。

同一个请求持续等待只计一次；回调完成、请求替换或离开就绪态后结束本次超时观察。后续请求再次超时才产生新事件。使用 HAL 毫秒 tick 的无符号差值，支持一次 tick 自然回绕；依赖 usb_task 继续获得调度，本身不能捕获 CPU 完全卡死的情况。

**超时只是观测事件，不能直接认定为故障或丢包。** 发送端未连接、未完成握手、没有数据发送或调试暂停，都可能导致正常接收等待超过 1 秒。结合 `ack_received`、通道寄存器、两端计数和实际业务判断。

## 复现时的 Watch

添加全局变量 `g_usb_rx_timeout_diag`，不需要再使用静态变量的固定地址：

| 字段 | 含义 |
|---|---|
| `threshold_ms` | 编译时采用的阈值；修改 Watch 不改变实际阈值 |
| `request_count` | 上层接收提交尝试累计数，提交失败也计数 |
| `callback_count / last_callback_tick` | 所有接收完成回调，包括控制帧和零长度包 |
| `active` | 当前请求是否已经触发超时且尚未被任务观察到结束 |
| `current_pending_ms` | 当前请求已等待时间；没有等待请求时为 0 |
| `timeout_count` | 超时请求数，同一次等待不会重复累计 |
| `max_observed_pending_ms` | 任务观察到的最大等待时间，不是结束时长的精确锁存 |
| `first` | 本次 F405 复位以来的首次超时快照，之后不覆盖 |
| `latest_index` | 最近一次超时在 `history` 中的下标 |
| `history[0..3]` | 最近四次超时的环形快照，以 `event_id` 判断先后 |
| `ended_count / last_end_tick` | 已结束的超时观察数和任务观察到结束的时间 |
| `last_end_reason` | 1=观察到回调后结束，2=离开就绪态，3=请求被清除或替换；不代表恢复操作成功 |

展开 `first` 与 `history[latest_index]`。`valid=1` 表示快照已写完；`valid=0` 时不要解释其内容。首个快照可能是启动阶段的正常等待，真正故障请结合最近快照和 `ack_received` 判断。

快照包括：请求编号和时间、等待时长、回调数、接收字节数、应用和 Host 状态、Host Timer、pending/ready/等待环形缓存标志、缓存余量、握手会话及 READY 完成数、CDC 收发状态、端点和缓冲区、HCD 通道状态、URB 状态、错误计数、PID/切换位、DMA 地址及本轮排查的 USB 全局/端口/通道寄存器。

`cdc_valid` 和 `hc_valid` 分别说明对应部分有效。按 CDC 当前 `InPipe` 选择通道，不固定为通道 4；通道下标越界不读取。短临界区避免 CPU 回调/任务切换导致软件状态交错；USB 硬件仍在运行，因此寄存器不是严格同一时刻的硬件锁存。

复现时先运行超过 1 秒，再保存整个诊断结构及主板发送计数，之后再暂停；长时间暂停本身会影响 USB 时序。记录只存在普通 RAM，复位/重新下载后重新开始，不会写入 SD，也不会跨复位保留。不要运行中手动清零结构。

## 修改及验证

- 功能源码仅修改 `User/Task/usb_task.c` 和 `.h`，原件保存在 `before`。
- 新增诊断结构 1112 字节，另有 4 字节内部请求编号；USB 任务原栈为 2048 字节，链接器对本次诊断路径的静态最大调用栈估计为 432 字节（不等于运行时高水位测量）。
- Keil AC6.22 验证项目编译：0 错误、0 警告，见 `build.log`。本次未下载、复位或操作板上寄存器。
- `test_timeout.py` 抽取实际两个诊断函数，模拟硬件验证阈值、去重、首次保留、历史回绕、tick 回绕、回调竞争、无效通道、IRQ 掩码恢复和重新提交；见 `test.log`。
- `firmware` 保存本次验证生成的 AXF、MAP、HEX，便于对应地址；正常使用项目重新编译下载即可，无需使用固定地址。

本次只记录超时后的现场，不追踪超时前每一次底层错误中断，不能据此保证确定最初的硬件触发原因。
